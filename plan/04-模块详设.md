## 二、数据结构

### 2.1 输入：车型档案（`Profile`）

```jsonc
{
  "schema": "ebikecheck.profile/1.0",
  "profile_id": "SYN-EB-001",
  "manufacturer": "示例车业（合成）有限公司",
  "uscc": "90000000SYN0000001X",          // 测试号段，虚构
  "model_design_date": "2025-10-01",        // 设计定型日（版本锚定主键）
  "market_date": "2025-11-15",              // 上市日（可选，锚定次键）
  "params": {
    "max_design_speed": {"value": "24.5", "unit": "km/h"},
    "vehicle_mass":     {"value": "61.2", "unit": "kg"},
    "battery_type":     {"value": "lead_acid"},
    "plastic_mass_ratio": {"value": "5.1", "unit": "%"},
    "nominal_voltage":  {"value": null, "unit": "V"},        // 未提供
    "motor_rated_power":{"value": "350", "unit": "W"}
  },
  "anti_tamper": {                          // 定性项，三态
    "battery_pack_no_extra_interface": true,
    "controller_no_jumper_mod": true,
    "speed_limiter_not_modifiable": true
  }
}
```

**参数值一律字符串**（避免 JSON float 精度损失），加载时转 `Decimal`。单位缺失不影响"有值"，但影响可比性 → 见 §四 单位策略。

### 2.2 输出：结论（`Finding`）

```jsonc
{
  "rule_id": "GB17761-2024-max_design_speed",
  "param": "max_design_speed",
  "standard": "GB 17761-2024",
  "clause": null,                     // 条款号待核对（见 §五 溯源纪律）
  "clause_status": "pending",
  "op": "<=",
  "limit": "25",
  "unit": "km/h",
  "observed": "24.5",
  "state": "compliant",               // compliant | non_compliant | not_applicable | not_provided
  "reason": null,                     // not_provided 时为原因码
  "severity": "normal"                // normal | warning（单位换算降级时）
}
```

原因码枚举：`missing` / `null_value` / `unparsable` / `unit_unknown` / `unit_incompatible` / `mapping_uncertain` / `condition_unknown` / `no_rule_for_param`。

### 2.3 汇总（`CheckResult`）

```jsonc
{
  "schema": "ebikecheck.result/1.0",
  "profile_id": "SYN-EB-001",
  "ruleset": {"file": "gb17761-2024.json", "sha256": "..."},
  "version_key": "GB17761-2024",
  "version_anchor": {"basis": "model_design_date", "value": "2025-10-01", "rule": ">=2025-09-01"},
  "counts": {"compliant": 4, "non_compliant": 1, "not_applicable": 2, "not_provided": 1},
  "overall": "non_compliant",         // 当全 not_applicable/无适用规则 → not_assessed
  "findings": [ ... ],
  "excluded_rules": [{"rule_id": "...", "status": "pending", "reason": "not_verified"}],
  "profile_sha256": "..."
}
```

**`overall` 取值**：`non_compliant` > `not_provided` > `not_assessed` > `compliant`（按"最弱结论优先"聚合）。**全 `not_applicable` 或零适用规则 → `not_assessed`，绝不输出 `compliant`**（02 §5.2）。

## 三、`engine/rules.py`：加载、schema 校验与门控

### 3.1 加载流程

```
load_ruleset(data_dir, version_key)
  1. 读 manifest.json → 定位分册文件 + 校验分册 sha256（与 manifest 登记值比对，不符即报错）
  2. 读分册 → schema 校验（见 3.2）
  3. 门控：status == "verified" 的条目进 check 路径；其余入 excluded
  4. 返回 Ruleset(meta, rules_effective, excluded)
```

### 3.2 schema 校验（失败即退出码 2，不放行任何判定）

| 校验项 | 规则 |
|---|---|
| 顶层 | 必含 `schema_version`/`standard`/`scope`/`rules`；`scope ∈ {vehicle, battery, charger}` |
| `standard` | 必含 `code`/`title`/`published`/`effective`/`status`；`status ∈ {current, superseded, abolished}`；日期为 `YYYY-MM-DD` |
| 每条规则 | 必含 `id`/`param`/`op`/`value`/`unit`/`clause`/`clause_status`/`source`/`status` |
| `id` | 全局唯一；非空 |
| `op` | ∈ 白名单 `<= >= < > == != in not_in range` |
| `value` | `status=verified` 时**必须非 null 且可 `Decimal`**（`in`/`not_in` 时可为字符串或列表）；`status=pending` 时**必须为 null**（防止"待核对却已填数"） |
| `clause_status` | ∈ `{verified, pending}`；`verified` 时 `clause` 必须非空；`pending` 时 `clause` 必须为 null（**不编造条款号**） |
| `source` | 必含 `kind`/`retrieved_on`；`kind ∈ {standard_meta, gov_qna, standard_text, to_verify}`；`kind != to_verify` 时 `url` 必填 |
| `applies_if` | `null` 或符合 §3.3 文法 |
| 交叉 | 同一分册内 `(param, clause_key)` 不得重复；`supersedes` 里的标准号必须在 manifest 中存在 |

### 3.3 `applies_if` 文法与求值

```
expr := null | {"param":str,"op":str,"value":any} | {"all":[expr]} | {"any":[expr]} | {"not":expr}
```

求值返回**三值逻辑**：`true` / `false` / `unknown`。

- 引用参数**未提供**或**值不可解析** → `unknown`。
- `all`：任一 `false` → `false`；无 `false` 且有 `unknown` → `unknown`；否则 `true`。
- `any`：任一 `true` → `true`；无 `true` 且有 `unknown` → `unknown`；否则 `false`。
- `not`：`true↔false`；`unknown` 保持 `unknown`。

**映射到结论**：

| 条件结果 | 规则结论 | 理由 |
|---|---|---|
| `true` | 走正常判定 | — |
| `false` | `not_applicable` | 该条不适用此车型 |
| `unknown` | `not_provided` + reason `condition_unknown` | **"不知道是否适用" ≠ "不适用"**；保守判未提供，绝不跳过 |

## 四、`engine/matrix.py`：判定算法

### 4.1 判定序（严格顺序，先短路）

```
for rule in rules_effective:
    cond = eval_applies_if(rule.applies_if, profile)
    if cond is False:  → not_applicable ; continue
    if cond is unknown: → not_provided(condition_unknown) ; continue

    raw = profile.params.get(rule.param)
    if raw is missing or raw.value is null: → not_provided(missing|null_value) ; continue
    if raw.unparsable:                      → not_provided(unparsable) ; continue

    observed, warn = normalize_unit(raw, rule.unit)
    if observed is None:                    → not_provided(unit_unknown|unit_incompatible) ; continue

    ok = compare(observed, rule.op, limit)
    → compliant / non_compliant ; severity = warning if warn
```

### 4.2 比较实现（Decimal，禁用 float）

- 所有数值 `Decimal(str)`；比较直接用 Decimal 运算符。
- `<=` `>=` `<` `>` `==` `!=` 逐一对 Decimal 或字符串（`==` 用于枚举参数如 `battery_type`）。
- `in` / `not_in`：值白名单成员判定（字符串枚举）。
- `range`：`[lo, hi]` 闭区间。

> **禁用 float**：边界扫描要检出"恰好等于限值"这类 1 个最小计量单位的差异，float 尾差不可接受（如 `5.5` 的二进制表示）。

### 4.3 单位策略（显式换算，降级为 warning）

| 情况 | 处置 |
|---|---|
| 单位一致 | 直接判定，`severity=normal` |
| **可显式无损换算**（g ↔ kg；m ↔ km；% ↔ ‰） | 换算后判定，`severity=warning`，`reason` 附换算说明 —— **只报不阻断** |
| 单位缺失 | 若参数为**无量纲**比较（枚举）→ 正常；否则 `not_provided(unit_unknown)` |
| 单位不可换算（如 mph → km/h 未登记换算） | `not_provided(unit_incompatible)` —— **绝不臆测汇率式换算** |

换算表放 `data/mapping/units.json`（M1），**M0 内置最小表**（kg/g、km/m、%/‰）。

### 4.4 边界枚举（M2/M4 基准）

- 从**规则包本身**推导边界，不硬编码：对每条 `value`，取 `value`、`value ± 最小计量单位`（按 `unit` 的精度约定：km/h → 0.1，kg → 0.1，% → 0.1）。
- 断言：`<=` 在 `== value` 时 `compliant`、`value+ε` 时 `non_compliant`。

## 五、溯源纪律（**本项目最容易被挑的点，写清楚**）

**现状（基准日 2026-10-14 实测）**：

- openstd.samr.gov.cn 提供**可直连的结构化元数据**（标准号/名称/发布日/实施日/状态/类别）→ 元数据 ✅ 已核对。
- gov.cn 官方问答页提供**逐字数值**（车速 25 km/h、铅蓄电池车型 63 kg、塑料占比 5.5%、防篡改三方面、过渡期）→ 数值 ✅ 已核对。
- **条款号（如 6.1.1）在两处均未出现**；openstd 标准全文依赖"查看详细/在线预览"（JS），未取得可直连解析载荷。

**因此的硬纪律**：

1. **不编造条款号**。`clause` 字段在核对前一律 `null`，`clause_status="pending"`，并在输出与报告中显式打印 `条款号待核对（M1 以正式标准文本复核）`。
2. **不编造数值**。问答未列明的参数（蓄电池标称电压、电动机额定功率等）→ `status="pending"`、`value=null`，**不进入核查路径**。
3. **门控按"判定所需"分作用域**（呼应 03 §三）：一条规则进入核查路径的判据是 **`status`（数值已核对）**；`clause` 是元数据、单独跟踪 `clause_status`。理由：数值是判定要素，条款号是可核证要素；把两者耦合成单一门控会导致"已核对数值也无法使用"，而把 `clause_status` 当唯一门又会让"已核对数值"被无谓阻断。**两者的当前状态都在产物中显式可见**，不存在"悄悄当作已核对"。
4. **M1 的入库前置**：以正式标准文本逐条补 `clause` + `clause_status="verified"`；补录前后**生成器整体重生成 + sha256 联动**。
5. 报告必须含**参数来源块**（发布机关/标准号/数值出处 URL/抓取日期/条款状态），使读者不开仓库也能核证。

> **决策登记**：本条属"动了会打挂基准与测试"的口径约定，见 [06-决策记录.md](06-决策记录.md) D-04/D-05。

## 六、`engine/version.py`：版本锚定

### 6.1 锚定规则

锚点来自 `manifest.json` 的 `version_anchors`（**不硬编码日期**）：

| 标准族 | 版本键 | 适用窗口 | 依据 |
|---|---|---|---|
| GB17761 | `GB17761-2024` | 设计/上市日 ≥ 2025-09-01 | 新标准实施日；2025-09-01 起新生产车辆须符合 |
| GB17761 | `GB17761-2018` | 设计/上市日 < 2025-09-01 | 历史车型对照 |

### 6.2 锚定算法

```
anchor_version(profile, manifest)
  basis = model_design_date (优先) → market_date (次) → None
  if basis is None: return AMBIGUOUS     # 不给日期 → 无法锚定 → 显式要求 --version-of
  for each anchor window: if basis in window → version_key
```

**过渡期口径（01 文 §决策记录）**：2025-09-01 起新生产车辆须符合新标准；销售过渡期至 2025-11-30。锚定**按车型设计/上市日期**取单一版本判定，**不混算**——即不出现"同一次核查里同时套用两版限值"。销售过渡期内的库存旧标准车型，其"按 2018 版判定"由 `--version-of 2018` 显式指定，报告在 `version_anchor.note` 里写明口径。

### 6.3 版本差异对照（FR-07，M4）

对同一份档案分别用两版规则集判定，输出差异表：

| 参数 | 2018 版 | 2024 版 | 差异类型 |
|---|---|---|---|
| `vehicle_mass`（铅蓄电池车型） | ≤ 55 kg | ≤ 63 kg | 数值放宽 |
| `plastic_mass_ratio` | 无要求 | ≤ 5.5% | **新增** |
| `over_speed_power_cutoff` | 无要求 | 超 25 km/h 停止动力输出 | **新增** |
| 防篡改 | 基础要求 | 三方面强化 | 强化 |

差异表本身也是**从两套规则包 diff 生成**（非手写），保证与规则包一致。

## 七、`report/`：报告（M5）

### 7.1 单一渲染源

```
report_sections(result) -> [Section]
Section = {id, title, kind: "table"|"paragraph"|"list", rows|text, columns?}
```

Markdown 渲染器与 XLSX 渲染器**都只消费 `report_sections()`** → "两格式内容一致"成为**结构性质**。配套测试：从两种产物抽出内容做逐项对等断言。

### 7.2 固定章节

| 章节 | 内容 | 纪律 |
|---|---|---|
| §1 报告头 | 规则包坐标（分册 + sha256 + manifest 生成时间）、工具版本、生成时间 | 无外链 |
| §2 输入事实 | 车型标识、设计/上市日期、参数表（含"未提供"显式列出） | 不改写输入 |
| §3 参数来源块 | 每个参数的依据：发布机关 + 标准号 + 条款号（或"待核对"）+ URL + 抓取日期 | NFR-09 |
| §4 逐项结论 | 逐参数四态 + 观测值 + 限值 + 条款依据 | 溯源完整性断言 |
| §5 越限项与整改建议 | 仅 `non_compliant` | 建议可执行 |
| §6 未评估与未提供 | `not_provided` / `not_applicable` / 被门控排除的规则清单 | **显式写出，不留空** |
| §7 版本坐标 | 版本锚定依据与窗口 | — |
| §8 证据指纹 | 档案 sha256 + 报告 sha256 + 规则包 sha256 | FR-11 |
| §9 免责声明 | 固定文本 | 01 §六 |

### 7.3 产物确定性

- Markdown：`\n` 行尾、无时间戳（生成时间取自输入或 `SOURCE_DATE_EPOCH` 式显式参数，不用系统时钟）。
- XLSX：自写最小 OOXML，`ZIP_STORED` + `create_system=0` + 固定 `date_time=(1980,1,1,0,0,0)`，文档属性时间戳固定 → **同输入逐字节一致**。
- **无外链**硬断言：单元格/正文/rels 内不得有 `http(s)://`（`TargetMode="External"` 出现即失败）。

## 八、`benchmark/`：评测基准（FR-13）

### 8.1 套件与门槛

| 套件 | 内容 | 门槛键（manifest.thresholds） |
|---|---|---|
| `rules` | 规则包 schema/门控自洽：`pending` 零进入、excluded 计数正确 | `truth_match_min` |
| `boundary` | 限值边界枚举（从规则包推导 ±最小计量单位） | `truth_match_min` |
| `synthetic` | 合成车型真值对账（逐项四态） | `truth_match_min` |
| `version` | 双版本对照：同档案两版期望差异 | `truth_match_min` |
| `mapping` | 字段映射准确率（M3） | `mapping_accuracy_min` |
| `reconcile` | 跨轮对账一致率（M3） | `reconcile_consistency_min` |

### 8.2 运行契约

```
ebikecheck bench [--only <suite>] [--json]
  退出码 0 = 全部被测套件达标
        1 = 有套件未达标（或计算非法）
        2 = 输入/坐标/用例名错误（--only 传未知名 → 2，绝不静默跳过）
```

- `--only` 部分运行时**不判定未测指标**（否则"没测"会被误报成"未达标"）。
- 门槛**只从 manifest 读**；缺失 → 退出码 2。
- **每套件配可证伪探活**：注入缺陷（阈值篡改 / 门控失效 / 真值期望篡改）→ 断言基准**必须**报未达标。
- 全量单次 < `bench_max_seconds`。

## 九、门禁工具

### 9.1 `tools/check_zero_literals.py`（FR-17）

- **禁用 token 集**：从 `tools/sources/*.json` 与 `data/rules/*.json` 收编全部数值（整数 + 对应小数 + 百分数串 + 日期串 + 标准号），词边界匹配。
- **扫描面**：`src/ebikecheck/**/*.py` + `benchmark/**/*.py` + `tools/*.py`（**含 docstring 与注释**）。
- **豁免口径**（写死并进 selftest）：
  - `< 10` 的小整数（精度约定/循环计数）；
  - 字段名与单位串（`km/h`、`kg`、`%`）——单位是标识不是限值；
  - 标准**号本身**在 `data/knowledge/` 与文档中允许（不在扫描面）；
  - 生成器读取的 **source 文件路径**字符串。
- `--selftest`：阳性对照（人造含 `25` 的临时文件必须被抓）+ 阴性对照（`km/h`、`range` 等不得误报）。

### 9.2 `tools/audit_desensitize.py`（FR-20）

- 三模式：`tracked`（`git ls-files` 全文本）、`history`（逐提交扫描 + **通道探活**）、`messages`（提交信息）。
- 分级：`HARD`（exit 1）/ `REVIEW`（人工豁免留档）/ `advisory`（只报不阻断，如长 hex 指纹——**本项目 sha256 指纹是文档化功能**）。
- 豁免：`*@users.noreply.github.com`（脱敏目标本身）、`git@github.com`/`github.com/<账号>`（发布固有公开元数据）、行内 `audit-allow` 标记。
- 输出**不回显敏感原文**（`文件:行号 [类别] xN`），报告因此可随仓留档。
- `--selftest` 含正/负对照：阳性（合成手机号/个人路径形态必须命中）+ 阴性（noreply、传输地址、sha256 hex 不得命中）。
- 模式源码里的词面用**片段拼接**构造，避免扫描器自命中。

### 9.3 仓库守门（并入测试）

- **EOL/CR 门**：`data/**/*.json`、`*.md`、`*.py` 出现 `\r` 即失败（`.gitattributes` 管检出，守门管写入）。
- **workflow YAML 可解析门**：用 PyYAML（dev extra）断言每个 workflow 可解析、每个 job 有 `runs-on`/`steps`、每个 checkout step 的 `with.fetch-depth == 0`。
- **确定性门**：重跑生成器 → `data/rules/` 逐字节一致。
