## 一、技术选型（逐项带理由与替代）

| 项 | 选型 | 理由 | 备选与为何不用 |
|---|---|---|---|
| 语言 | **Python 3.8+** | 核心层零第三方依赖即可交付；3.8 是本机底线，CI 也覆盖 3.12 | 不用 Node/Go：桌面交付需 PySide6 + PyInstaller 生态，Python 最省事 |
| 核心层 | **纯标准库** | NFR-02：规则加载/判定/基准/报告全离线可复现；打包体积小、无供应链风险 | 不用 pandas：只做逐项限值比较，标准库足够，且 pandas 会污染"零依赖"承诺 |
| 规则包格式 | **JSON**（生成器冻结） | 人可审、diff 友好、零依赖解析、易于挂 sha256 | 不用 YAML（需第三方库）/ TOML（3.8 无 `tomllib`） |
| CLI | **argparse**（标准库） | 零依赖；子命令 + 退出码语义可控 | 不用 click/typer（第三方） |
| 报告-人读 | **自写 Markdown 渲染器** | 与机读格式共用**单一渲染源**（FR-12）；零依赖 | — |
| 报告-机读 | **自写最小 OOXML writer**（`ZIP_STORED` + 固定 `create_system`/`date_time`） | NFR-04：逐字节可复现。引 openpyxl 会让 zip 元数据（宿主系统标识、时间戳）漂移 | 不用 openpyxl 做**冻结产物**；它仅作可选"导出便利"通路（M5 决策） |
| 桌面 | **PySide6**（可选 extra） | 官方 Qt 绑定，PyInstaller 支持成熟 | 不用 Tkinter：表格/多页签表现力不足 |
| 打包 | **PyInstaller onedir**，GUI 需 **≥6** | 5.x 扫 PySide6 字节码确定性崩（`Instruction object is not iterable`） | 不用 PyInstaller 5.x 打 GUI |
| 基准 | 标准库 | 零 API 依赖、离线可跑（NFR-06 < 1 秒） | — |
| LLM | **不使用** | 纯确定性规则 + 结构化输入，无解析兜底需求（见 02 §二） | 用了会引入不可复现与联网风险 |

## 二、分层架构

```
┌──────────────────────────────────────────────────────────┐
│ 表现层（薄，零判定逻辑）                                   │
│   cli.py（argparse 子命令）    gui/（PySide6，M5）         │
│   职责：解析参数、调 service、渲染结果、定退出码             │
└────────────────────┬─────────────────────────────────────┘
                     │ 唯一入口（GUI 只准经 service）
┌────────────────────▼─────────────────────────────────────┐
│ 服务层 service.py（编排单一事实源）                        │
│   selfcheck() / check_profile() / scan_dir() /            │
│   compare_rounds() / export_report() / run_bench()        │
│   职责：串装配顺序（加载→门控→判定→汇总→溯源断言）           │
└────────────────────┬─────────────────────────────────────┘
┌────────────────────▼─────────────────────────────────────┐
│ 引擎层（确定性内核，纯函数优先）                            │
│   engine/rules.py     规则加载 + schema 校验 + status 门控 │
│   engine/matrix.py    参数 × 限值判定（四态）               │
│   engine/mapping.py   字段映射引擎（列名 → 标准参数名）      │
│   engine/reconcile.py 跨轮对账（三集合）                    │
│   engine/version.py   版本锚定（设计/上市日期 → 规则集）     │
│   engine/evidence.py  sha256 指纹 + 溯源断言                │
│   engine/findings.py  结论数据结构（Finding/Report 模型）    │
└────────────────────┬─────────────────────────────────────┘
┌────────────────────▼─────────────────────────────────────┐
│ 数据层（随包白名单，生成器冻结产物）                        │
│   data/rules/     限值规则包（三标准分册 × 双版本 + manifest）│
│   data/mapping/   字段映射表                                │
│   data/truth/     合成车型档案 + 真值库                     │
│   data/knowledge/ 依据索引 + 官方快照（sha256 登记）          │
└──────────────────────────────────────────────────────────┘
```

### 2.1 依赖方向（硬约束，由测试守住）

- `data` ← `engine` ← `service` ← `cli` / `gui`。**禁止反向**。
- `gui` **不得**直接 import `engine.*`（只准经 `service`）→ AST 静态门禁（FR-15）。
- `engine` 与 `bench` **不得** import 表现层，也不得 import 第三方包（NFR-02）。
- `cli` 模块**顶层不得** import `gui`/`PySide6`（惰性导入 + AST 断言）。

### 2.2 为什么服务层要单独存在

CLI 与 GUI 若各自串一遍"加载 → 门控 → 判定 → 汇总"，两条通路的判定口径必然漂移（最隐蔽的缺陷）。把编排**上收成 `service.py` 的一组公开函数**：两者消费同一函数，于是"CLI 结论 == GUI 结论"成为**结构性质**而非人工承诺。测试用**三方对账**（CLI stdout 数值 == 直接调 service 的字段 == 报告章节里的数值）断言行为等价，而不是断言"都调了同一个函数"。

## 三、规则包 schema（v1）

### 3.1 目录与命名

```
data/rules/
  manifest.json                    索引：分册清单 + 版本坐标 + 门槛 + 生成器版本
  gb17761-2024.json                整车（现行）
  gb17761-2018.json                整车（历史对照）
  gb43854-2024.json                锂电池
  gb42296-2022.json                充电器
```

分册文件名 = `标准号小写-版本`；每册自带 `standard` 元数据块，**互不混用**（FR-04/05）。

### 3.2 分册结构

```jsonc
{
  "schema_version": "1.0",
  "standard": {
    "code": "GB 17761-2024",
    "title": "电动自行车安全技术规范",
    "issuer": "国家市场监督管理总局、国家标准化管理委员会",
    "published": "2024-12-31",
    "effective": "2025-09-01",
    "status": "current",              // current | superseded | abolished
    "supersedes": ["GB 17761-2018"],
    "mandatory": true
  },
  "scope": "vehicle",                 // vehicle | battery | charger
  "rules": [
    {
      "id": "GB17761-2024-6.1.1-speed",
      "param": "max_design_speed",
      "op": "<=",
      "value": "25",                  // 一律字符串承载，加载时转 Decimal（防 float 尾差）
      "unit": "km/h",
      "applies_if": null,             // 或 {"all":[...]} / {"any":[...]}
      "clause": "6.1.1",
      "clause_excerpt": "……最高设计车速不超过 25 km/h……",
      "source": {"kind": "gov_qna", "url": "https://www.gov.cn/...", "sha256": "..."},
      "status": "verified",           // verified | pending
      "verified_on": "2026-10-14",
      "notes": ""
    }
  ]
}
```

### 3.3 关键字段纪律

| 字段 | 纪律 |
|---|---|
| `value` | **字符串**承载数值；加载时 `Decimal(value)`，判定全链路 Decimal（避免 float 尾差把边界判错） |
| `op` | 白名单枚举：`<=` `>=` `<` `>` `==` `!=` `in` `not_in` `range`。出现白名单外 → schema 校验失败退出码 2 |
| `applies_if` | 条件表达式（见 3.4）；缺省 `null` 表示恒适用 |
| `clause` | **必填非空**；无条款号者不得建条目（"不编造标准内容"） |
| `source` | 必填；`kind ∈ {openstd_meta, gov_qna, standard_text}`；`pending` 条目可 `source.kind="to_verify"` |
| `status` | 只有 `verified` 进核查路径；**是门控的唯一判据** |
| `unit` | 与档案值单位一致性由映射层归一（如 g ↔ kg 走显式换算并只报 `warning`） |

### 3.4 条件表达式（`applies_if`）

结构化的**白名单小语言**（不用 eval，避免注入与不确定性）：

```jsonc
{"param": "battery_type", "op": "==", "value": "lead_acid"}
{"all": [ {...}, {...} ]}
{"any": [ {...}, {...} ]}
{"not": {...}}
```

求值规则：引用的参数**未提供** → 条件判定为 `unknown` → 该规则结论 = `not_applicable` 的**兄弟态**：
**M0 起先保守处理为 `not_provided` 并附 reason `condition_unknown`**（不冒险判"不适用"，因为"不知道是否适用"不等于"不适用"）。

### 3.5 manifest.json

```jsonc
{
  "schema_version": "1.0",
  "generated_by": "tools/gen_rulesets.py",
  "generator_version": "1.0.0",
  "rulesets": [
    {"file": "gb17761-2024.json", "standard": "GB 17761-2024", "scope": "vehicle",
     "version_key": "GB17761-2024", "effective_from": "2025-09-01", "sha256": "..."}
  ],
  "version_anchors": [
    {"standard_family": "GB17761", "version_key": "GB17761-2024",
     "applies_from": "2025-09-01", "note": "新生产车辆适用"},
    {"standard_family": "GB17761", "version_key": "GB17761-2018",
     "applies_until": "2025-09-01", "note": "历史车型对照"}
  ],
  "thresholds": {                     // 验收门槛：数据非代码（NFR/FR-13）
    "mapping_accuracy_min": "0.98",
    "reconcile_consistency_min": "1.0",
    "truth_match_min": "1.0",
    "bench_max_seconds": "1.0"
  }
}
```

> **门槛随 manifest 下发**：基准层只读 `thresholds`，缺失即报配置错误（退出码 2），**不得回落代码默认值**——内联门槛就是"抄进代码的第二份真相"。

## 五、CLI 契约与退出码

```bash
ebikecheck selfcheck [--json]                        # 数据目录 + 规则加载 + 门控计数
ebikecheck check <档案.json> [--json] [--version-of 2024|2018|auto]
ebikecheck version-anchor <日期>                     # 版本锚定查询（M1）
ebikecheck bench [--only <suite>] [--json]
ebikecheck scan <目录|清单> [--baseline <上轮.json>] [--out <目录>]   # M3
ebikecheck report <结果.json> --format md|xlsx --out <路径>          # M5
ebikecheck gui                                       # M5（惰性导入 PySide6）
ebikecheck version
```

### 5.1 退出码三语义（锁进测试，FR-14/NFR-05）

| 码 | 含义 | 出现场景 |
|---|---|---|
| **0** | 通过 | 核查无 `non_compliant`（含"全 not_provided"）/ bench 全达标 / 用法正确且成功 |
| **1** | 检出不符合或未达标 | 存在 `non_compliant` 结论 / bench 指标未达门槛 / 报告溯源断言失败 |
| **2** | 用法或输入错误 | 参数错误 / 文件不存在 / schema 非法 / `--only` 未知名 / 门槛缺失 |

> **`not_provided` 不改退出码**：它是"未判定"，不是"检出不符"。"有一件没判定"与"判出违规"混在一个码里会让 CI 误判。批量扫描中失败件同理单列（FR-09）。

## 六、数据目录查找优先级（`find_data_dir`）

```
1. 显式参数（--data-dir）                      最高
2. 环境变量 EBIKECHECK_DATA_DIR
3. 冻结态：sys._MEIPASS/data                 （PyInstaller 6）
   → exe 目录/_internal/data                 （PyInstaller 6 兼容）
   → exe 目录/data                           （PyInstaller 5 平铺布局）
4. 源码态：包内 ../../data → CWD 上溯找 data/manifest.json  兜底
```

- 冻结态**必须**解析到 dist 之内（`commonpath([exe_dir, data_dir]) == exe_dir`）→ `--selftest` 断言（非冻结态该项返回 `None` 而非 FAIL）。
- 改优先级属于"动了会打挂测试"的口径变更，须同步改测试与 [06-决策记录.md](06-决策记录.md)。

## 七、错误处理与降级原则

| 场景 | 处置 |
|---|---|
| 规则 schema 非法 | 立即退出码 2，**不放行任何判定** |
| 某条目 `status=pending` | 过滤出核查路径，记入 `excluded`，在输出与报告显式列出 |
| 档案缺参数 | 判 `not_provided` + reason 码（`missing` / `unparsable` / `unit_unknown` / `mapping_uncertain`） |
| 档案单位可显式换算（g→kg） | 换算后判定，结论降级为 `warning` 级（只报不阻断） |
| 批量中单件坏 | **隔离不中断**：记 `failed` + 原因码，继续跑 |
| 可选依赖缺失（openpyxl 等） | 惰性导入 + try 包住**从 import 到调用完成**整条路径；冻结态提示"本发行包未内嵌"，源码态提示 pip 安装 |

## 八、测试与 CI 策略

- **pytest**，`tests/` 无 `__init__.py` 布局；offline，无网络。
- CI 矩阵：`windows×{3.8, 3.12}` + `ubuntu×{3.12}`（旧解释器只在 Windows 守，Ubuntu 新镜像对 3.8 支持存疑）。
- CI 必须 `fetch-depth: 0`（脱敏历史扫描依赖全量 git 历史；浅克隆会**静默削弱成空验**），并加守门断言"每个 checkout step 的 `with.fetch-depth == 0`"。
- core-only 守门 job 装 `-e ".[dev]"` 而非 `-e .`：**测试框架 pytest 本身住在 dev extra**，装 core-only 跑测试会整批 `ImportError`。
- Linux 若跑 GUI 验收需补 Qt 系统库：`libegl1 libgl1 libxkbcommon0 libdbus-1-3 libfontconfig1`。
- workflow YAML 必须可解析（step 名含 `: ` 的纯量会致整份非法 → GitHub 不建任何 job），配守门测试。
