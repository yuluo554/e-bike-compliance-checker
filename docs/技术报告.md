# 电动自行车合规核查工作台 —— 技术报告

**项目**：e-bike-compliance-checker（GB 17761—2024 双版本规则集 · 三维限值矩阵 · 批量对账 · 证据指纹 · 桌面交付）
**基准日**：2026-10-14（M5 收尾）
**交付形态**：PySide6 桌面应用 exe（PyInstaller onedir）+ CLI 双入口 + 核心代码框架 + 技术报告 + 合成数据与真值库 + 演示素材（`docs/assets/demo-overview.gif` 及三帧 PNG，程序化产出）

---

## 一、问题与约束

### 1.1 要解决的问题

GB 17761—2024《电动自行车安全技术规范》于 2025-09-01 实施（替代 GB 17761—2018），对整车/蓄电池/充电器提出三维限值要求。厂家参数表列名不统一、新旧标准版本并存（销售过渡期）、条款号与数值的可核证性，使"逐款人工对照 Excel 校验表"既慢又不可审计。本工具把这件事变成：**版本化限值规则包 + 参数矩阵判定 + 批量对账 + 证据指纹**的确定性流程。

### 1.2 硬约束

| 约束 | 落点 |
|---|---|
| 全本地处理存储、零上传 | 引擎/CLI/GUI 均无网络调用；报告无外链硬断言 |
| 不编造条款号/数值 | `clause_status` 与 `status` 分门控；未核对条目 `pending` 且 value 必须为 null |
| 核心层零第三方依赖 | 引擎纯标准库（AST 门禁守门）；PySide6/pyinstaller 只进 extras |
| 界面结论 == CLI 结论 | 编排上收 `service.py` 单一事实源，GUI/CLI 只消费同一组公开函数 |
| 产物确定性 | 生成器 `--check` 逐字节冻结；报告逐字节可复现；演示素材两次生成 sha256 一致 |

## 二、架构

### 2.1 分层

```
data/（规则包·真值库·映射表·依据索引）
   ↑
engine/（rules 门控 → matrix 判定 → findings 四态/三维聚合；version 锚定；
         mapping 列名映射；reconcile 对账；version_diff 差异引擎）
   ↑
service.py（编排单一事实源：selfcheck / check_profile 三通路 / scan_dir /
         compare_rounds / version_diff* / evidence_chain / export_report）
   ↑
cli.py（argparse 9 子命令）      gui/（PySide6 四页签，只调 service）
```

**禁止反向依赖**：`gui` 不得 import `engine.*`（AST 门禁）；`cli` 顶层不得 import `gui`/`PySide6`（惰性导入 + AST 门禁）。由此"界面与命令行结论一致"成为结构性质而非人工承诺。

### 2.2 关键设计决策（限值规则化方法）

1. **规则包是唯一限值来源**。限值数值只存在于 `data/rules/*.json`（生成器从来源登记生成、`--check` 逐字节冻结、manifest 挂 sha256）；源码内出现任何限值数值即门禁失败（`tools/check_zero_literals.py`，把规则包全部数值收编为禁用 token 扫描源码含 docstring）。当前 7 个禁用 token 零命中。
2. **四态结论，绝无假合规**。`compliant / non_compliant / not_applicable / not_provided` 四态分离；"未提供"与"不适用"都不是通过；整体结论按最弱优先（`non_compliant` > `not_provided` > `not_assessed` > `compliant`）聚合，零参与维度 → `not_assessed`，绝不输出 `compliant`。
3. **门控按"判定所需"分作用域**。数值是判定要素（`status` 门控），条款号是可核证要素（`clause_status` 单独跟踪），两者解耦——已核对数值不被条款号缺失无谓阻断，且两者状态都在产物中显式可见。
4. **版本锚定按车型日期**，不混算：设计定型日/上市日 → manifest 锚点窗口 → 单一版本判定；显式 `--version-of` 覆盖（过渡期库存旧标准车型按 2018 版判定）。
5. **全链路 Decimal**，禁用 float——边界枚举要检出"恰好等于限值"这类 1 个最小计量单位的差异。
6. **基准从规则包推导，不读真值库**：`boundary`/`rule_driven` 套件的端点全部由规则的 `op/value/unit` 推出，**不写死规则 id**——新增规则自动进枚举（`test_new_numeric_rule_is_enumerated_without_touching_probe_code` 守门）。

### 2.3 参数矩阵与三维判定

一份车型档案同时得到**整车（GB 17761）+ 蓄电池（GB 43854）+ 充电器（GB 42296）**三维结论，各挂自身标准号、规则分册与 sha256；统一结论只聚合"参与维度"——标准尚未生效（生效日晚于档案锚定日）或零生效规则（首期不参数化）的维度显式记录理由后不参与聚合。

判定序（先短路）：`applies_if` 三值逻辑（假 → 不适用；unknown → 未提供，**"不知道是否适用" ≠ "不适用"**）→ 参数缺失/空值 → 不可解析 → 单位不可用 → 比较。单位策略：可显式无损换算（kg↔g 等）则换算后判定并降级 `warning`；不可换算绝不臆测。

### 2.4 字段映射设计（M3）

厂家列名 → 标准参数名的映射表是数据侧唯一来源（`data/mapping/mapping.json`，生成器生成 + 冻结）。三档处置：

- 唯一匹配 → 归一判定（含 11 类单位别名，与引擎换算表同一张表消费）；
- **歧义列名**（如「车速」对多个候选参数）→ 对全部候选注入不确定标记 → `not_provided(mapping_uncertain)`，**绝不猜**；
- 未登记 → `missing`。

映射准确率基准 84/84（门槛 0.98 由 manifest 下发）。

### 2.5 版本差异引擎（M4）

差异表**从两版规则包 diff 生成，不是手写**：逐参数按 `applies_if` 分支配对（"旧版无条件 vs 新版条件拆分"逐分支各配一行，每行携带配对依据可溯源）；收紧/放宽只对同向阈值运算符成立，`==` 目标变化如实记 `value_changed` 不硬套方向；旧→新方向按分册发布日排序（锚点表顺序不承诺时间序）。当前实测（2018 → 2024）：新增 7 + 铅酸质量分支放宽 1 + 不变 2。

## 三、证据链（FR-11）

- **档案指纹**：文件级 sha256（加载时落定）+ 内容级规范化 JSON sha256（与路径无关），用途分开登记；
- **溯源完整性硬断言**：每条 finding 按 `(param, standard)` 必须能在该维度 `source_blocks` 找到来源块；档案指纹缺失即拒——不满足即抛 `TraceabilityError` **拒绝交出**，不降级为警告；
- **报告指纹**：对结果载荷的规范 JSON 取 sha256，报告被改动即可检出（测试验证篡改观测值后指纹变化）；
- **报告导出前置硬门**：`export_report` 先装配证据链（内部先跑溯源断言），断言失败拒绝导出。

参数来源块（NFR-09）让读者**不开仓库也能核证**：每个生效数值挂发布机关/标准号/条款号（或"待核对"）/来源类别/抓取日期；依据索引对 6 份官方快照逐份挂 sha256。

## 四、报告导出（M5-1）

- **单一渲染源**：`report/sections.py::report_sections()` 返回九章节结构化载荷（§1 报告头/§2 输入事实/§3 参数来源块/§4 逐项结论/§5 越限与整改/§6 未评估与门控排除/§7 版本坐标与两版差异/§8 证据指纹/§9 免责声明）；Markdown 与 XLSX 两渲染器**只消费它**，两格式内容一致是结构性质（测试做逐项对等断言）；
- **无外链红线**：来源 URL 只渲染成"来源编号"（原始链接留在数据侧依据索引）；装配后跑无外链硬断言，MD 正文与 XLSX 单元格不得出现 `http(s)://`；
- **逐字节可复现**：生成时间取输入侧（显式参数，不用系统时钟）；XLSX 自写最小 OOXML（`ZIP_STORED` + 固定 `date_time=(1980,1,1,0,0,0)` + `create_system=0`，不生成 docProps 时间戳）；渲染器不得 import 时间/随机模块（AST 断言）。

## 五、桌面交付（M5-2/M5-3）

- **PySide6 四页签**：单车核查（三维结论表 + 证据指纹 + 一键导出报告）/ 批量扫描（结论分布 + 失败件隔离表）/ 跨轮对账（三集合）/ 版本差异（规则包 diff + 同档案两版结论对照）。界面零判定逻辑：取数全部经 `service`，AST 门禁禁止 import 引擎层与判定痕迹；
- **PyInstaller onedir 双 exe**（PyInstaller 6.x；5.x 扫 PySide6 字节码确定性崩）：`ebikecheck-gui.exe` + `ebikecheck-cli.exe` 共享 `_internal/data`；
- **中立目录冻结态自检**：把产物目录拷到仓库外运行，`selfcheck` 实测 `frozen=True`、`data_dir_within_exe_dir=True`（数据落在 exe 目录内），CLI 核查/导出与 GUI 启动均通过。

## 八、已知边界与如实声明

1. **GB 17761—2018 官方不提供全文**（已废止，openstd 明示不提供阅读服务）→ 条款号如实 `pending`，限值经 2024 版官方问答对旧限值的引述核对，不编造；
2. GB 43854 / GB 42296 首期不做参数化的条目 → `pending` + 理由入 `notes`，不进入核查路径但在报告门控排除清单显式列出；
3. CI 于 M6 脱敏发布期首推真实运行：首跑失败（dev extras 缺 Pillow，与干净环境验证暴露的是同一缺口）→ 修复提交 e117602 → **三矩阵全绿**（windows py3.8/py3.12 + ubuntu py3.12）；发布 Release v0.1.0 附件 sha256 留档并经真下载核对一致（[release-sha256.md](release-sha256.md)）；
4. 输出为基于标准限值的**合规检查发现**，不构成产品合格判定、检测结论或行政认定；正式结论以具备资质的检验检测机构报告与市场监管部门口径为准。
